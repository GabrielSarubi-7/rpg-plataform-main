RPG PLATFORM — PLANO MESTRE PARA IMPLEMENTAÇÃO DO 3D REAL
Documento técnico de execução para o Astra
Data da especificação: 2026-09-09

======================================================================
0. OBJETIVO DESTE DOCUMENTO
======================================================================

Este documento deve ser tratado como uma especificação de implementação.

OBJETIVO PRINCIPAL:
Transformar o RPG Platform em uma VTT capaz de renderizar e editar mapas 3D reais,
sem destruir nem reescrever as funcionalidades que já existem no modo 2D/2.5D.

O resultado desejado não é apenas um "mapa inclinado".
O modo 3D deve possuir uma cena tridimensional real, com:
- câmera em perspectiva;
- eixos X/Y/Z;
- profundidade real;
- modelos GLB/GLTF;
- luzes;
- sombras;
- paredes;
- portas;
- múltiplos andares;
- objetos;
- tokens 2D em billboarding;
- tokens com modelos 3D;
- raycasting;
- seleção;
- movimentação;
- grid;
- medição;
- áreas de efeito;
- Fog of War;
- visibilidade;
- eventos;
- áudio espacial;
- multiplayer;
- permissões;
- persistência;
- ferramentas do GM;
- editor de cena.

REGRA MAIS IMPORTANTE:
NÃO reescrever o projeto do zero.

O RPG Platform já possui uma arquitetura full-stack útil e madura:
React + TypeScript + Vite + Zustand + Socket.IO + Express + Prisma + PostgreSQL.
Ela deve ser aproveitada.

O 3D deve entrar como uma NOVA CAMADA DE RENDERIZAÇÃO e como uma evolução
dos tipos de mapa/tokens, sem remover:
- autenticação;
- campanhas;
- personagens;
- fichas;
- ações;
- rolagens;
- turnos;
- chat;
- áudio global;
- mapas existentes;
- tokens existentes;
- Fog atual;
- permissões;
- Socket.IO existente;
- persistência existente.

O modo 2D precisa continuar funcionando durante toda a implementação.

2. COMO O "2.5D" ATUAL FUNCIONA E POR QUE NÃO É 3D REAL
======================================================================

O modo atual usa projeção manual e transformações CSS.

Arquivos importantes:

apps/client/src/features/map/MapCanvas.tsx
apps/client/src/features/map/hooks/useCamera.ts
apps/client/src/features/map/utils/coords.ts
apps/client/src/features/tokens/components/Token.tsx
apps/client/src/features/tokens/components/TokenLayer.tsx

A câmera atual possui:

interface Camera {
  centerX: number;
  centerY: number;
  zoom: number;
  pitch: number;
  yaw: number;
}

O mapa continua sendo um plano DOM 2D.

O "3D" é simulado por:
- perspective CSS;
- rotateX;
- rotateZ;
- projeção manual worldToScreen;
- profundidade simulada;
- token projetado sobre a tela;
- elevação convertida em pixels;
- billboard simulado com CSS.

Isso é útil como modo 2.5D, mas tem limitações estruturais:
- não existe depth buffer real;
- não existe geometria 3D real;
- não existe raycasting 3D;
- não existe oclusão física;
- não existem luzes reais;
- não existem sombras reais;
- não existe carregamento de mesh GLB;
- não existe camera PerspectiveCamera;
- não existe scene graph 3D;
- objetos não ocupam volume real;
- paredes não bloqueiam câmera/luz por geometria;
- diferentes andares são difíceis de representar corretamente;
- colisões 3D ficariam artificiais;
- efeitos visuais avançados seriam difíceis.

CONCLUSÃO:
Não tentar transformar esse renderer DOM/CSS em um engine 3D.
Preservá-lo como modo "2.5d" legado.

Criar um renderer 3D real em paralelo.

======================================================================
3. DECISÃO DE ENGINE
======================================================================

Foram consideradas quatro opções principais.

----------------------------------------------------------------------
3.1 THREE.JS PURO
----------------------------------------------------------------------

Vantagens:
- controle completo;
- biblioteca madura;
- WebGL/WebGPU;
- enorme ecossistema;
- GLTF;
- iluminação;
- animações;
- raycasting;
- shaders;
- pós-processamento.

Desvantagens:
- integração mais imperativa com React;
- mais trabalho para sincronizar lifecycle;
- mais código manual para componentes.

Bom tecnicamente, mas não é a opção ideal para este projeto React.

----------------------------------------------------------------------
3.2 THREE.JS + REACT THREE FIBER
----------------------------------------------------------------------

RECOMENDAÇÃO PRINCIPAL.

React Three Fiber é um renderer React para Three.js.

Vantagens específicas para este projeto:
- o frontend já é React;
- funciona com Zustand;
- permite componentes declarativos;
- permite reutilizar o estado atual;
- eventos de pointer/raycast são integrados;
- integração natural com componentes;
- excelente ecossistema;
- Drei fornece câmera, TransformControls, helpers, Html, Environment etc.;
- continua permitindo acessar Three.js diretamente;
- não exige reconstruir a UI da plataforma;
- permite manter UI HTML sobre o Canvas;
- pode ser lazy-loaded.

Compatibilidade:
O projeto usa React 18.
Portanto NÃO instalar automaticamente a versão mais nova do R3F se ela exigir React 19.

Usar:
- @react-three/fiber v8 para React 18;
- @react-three/drei v9 para a linha React 18;
- se Rapier for usado, @react-three/rapier v1 para React 18.

Comando base sugerido:

npm install -w client three @types/three @react-three/fiber@8 @react-three/drei@9 three-mesh-bvh

Física opcional, somente quando chegar à fase de colisões/objetos físicos:

npm install -w client @react-three/rapier@1

NÃO adicionar Rapier na primeira etapa sem necessidade.

----------------------------------------------------------------------
3.3 BABYLON.JS
----------------------------------------------------------------------

Babylon é excelente e possui muitas funcionalidades "batteries included":
- WebGL/WebGPU;
- câmeras;
- iluminação;
- física;
- Havok;
- partículas;
- GUI;
- picking;
- áudio;
- animação;
- ferramentas.

Seria uma boa escolha se o projeto estivesse começando do zero como um jogo 3D.

Não é a primeira escolha aqui porque:
- introduziria um segundo modelo arquitetural grande;
- a integração com o React atual seria menos natural;
- exigiria mais adaptação de stores/componentes;
- o projeto já tem um bom shell de VTT que não precisa ser substituído.

----------------------------------------------------------------------
3.4 PLAYCANVAS
----------------------------------------------------------------------

PlayCanvas em 2026 possui:
- WebGL2;
- WebGPU;
- React integration;
- engine próprio;
- editor visual;
- PBR;
- pós-processamento;
- recursos modernos.

É forte para experiências 3D completas e projetos criados em torno do próprio engine.

Não é a recomendação principal porque o RPG Platform já tem:
- editor próprio;
- sockets próprios;
- stores;
- mapas;
- fichas;
- regras;
- UI;
- backend.

Adotar PlayCanvas como núcleo empurraria o projeto para uma arquitetura centrada
no engine em vez de aproveitar a arquitetura React já existente.

----------------------------------------------------------------------
3.5 UNITY/GODOT EXPORTADO PARA WEB
----------------------------------------------------------------------

NÃO usar.

Motivos:
- bundle muito maior;
- runtime separado;
- integração ruim com a UI React existente;
- duplicação de estado;
- sockets e autenticação mais difíceis;
- deployment mais complexo;
- risco de transformar uma VTT web modular em dois aplicativos colados.

4. WEBGL OU WEBGPU
======================================================================

Para a primeira versão de produção:

USAR WebGLRenderer.

Motivo:
Three.js já possui WebGPURenderer moderno com fallback para WebGL 2,
mas o próprio projeto Three ainda trata essa linha como experimental em alguns
cenários e existem diferenças de materiais/pós-processamento.

A arquitetura deve ser preparada para trocar o renderer futuramente.

Criar algo como:

scene3d/renderer/createRenderer.ts

Primeiro:
- WebGLRenderer padrão do R3F.

Futuro:
- opção experimental "WebGPU";
- feature flag;
- detectar compatibilidade;
- nunca quebrar WebGL 2.

NÃO bloquear o projeto esperando WebGPU.

======================================================================
10. SISTEMA DE COORDENADAS
======================================================================

Essa decisão precisa ser consistente em TODO o projeto.

Usar padrão Three.js:

X = horizontal
Y = altura
Z = profundidade

Definir:

1 unidade Three.js = 1 célula do grid.

O mapa atual usa:
- token.x em pixels;
- token.y em pixels;
- cellSize em pixels;
- elevation em pés;
- D&D atual considera 1 célula = 5 ft.

Conversão recomendada.

LEGACY -> 3D

Para um token:

tokenWidthPx = widthCells * cellSize
tokenHeightPx = heightCells * cellSize

centerXCells = (token.x + tokenWidthPx / 2) / cellSize
centerZCells = (token.y + tokenHeightPx / 2) / cellSize

worldX = centerXCells
worldZ = centerZCells
worldY = elevationFt / feetPerCell

No sistema atual:
feetPerCell = 5

Portanto:

worldY = elevation / 5

3D -> LEGACY

token.x = worldX * cellSize - tokenWidthPx / 2
token.y = worldZ * cellSize - tokenHeightPx / 2
token.elevation = worldY * feetPerCell

Criar funções em:

scene3d/utils/coordinates3d.ts

Exemplo:

legacyTokenToWorldPosition(token, cellSize)
worldPositionToLegacyToken(...)
feetToWorldUnits(feet)
worldUnitsToFeet(units)
pixelsToWorldUnits(px, cellSize)
worldUnitsToPixels(units, cellSize)

NÃO duplicar essas fórmulas em componentes diferentes.

11. NÃO MUDAR O TARGETING DO COMBATE NO PRIMEIRO MOMENTO
======================================================================

O projeto já possui:

shared/rules/targetingRules.ts

Ele calcula:
- círculo;
- quadrado;
- cone;
- linha;
- single target;
- melee;
- esfera conceitual;
- cilindro conceitual.

Hoje ele trabalha em X/Y do mapa e usa pixelsPerFoot.

IMPORTANTE:
Na primeira versão 3D, manter o targeting autoritativo EXISTENTE.

O renderer 3D:
1. faz raycast no chão;
2. converte worldX/worldZ para pixel X/Y;
3. chama resolveActionTargeting existente;
4. usa affectedTokenIds retornados;
5. apenas RENDERIZA o preview em 3D.

Isso evita que o modo 2D e 3D tenham regras diferentes.

Exemplo:
- uma Fireball em 3D pode ser mostrada como esfera;
- mas a seleção dos alvos continua usando a lógica existente na primeira fase.

Fase futura:
criar targetingRules3d.ts com altura real e volume 3D.

Só ativar targeting 3D completo com opção explícita.
Não alterar silenciosamente a regra de combate das campanhas antigas.

17. GROUND PLANE
======================================================================

O mapa atual possui:

widthCells
heightCells
cellSize
backgroundImage

No 3D:
o tamanho físico da malha deve ser:

width = widthCells
depth = heightCells

Criar PlaneGeometry ou BoxGeometry bem fino.

Orientação:
plano horizontal X/Z.

A imagem do mapa deve virar texture.

Cuidado com UV:
a imagem precisa preservar a mesma orientação do modo 2D.

Se ficar invertida verticalmente, ajustar texture.flipY ou UV, não inverter
o sistema de coordenadas inteiro.

O plano deve:
- receiveShadow = true;
- ser raycastable;
- ter userData identificando que é ground;
- ser usado para movimentação.

19. CÂMERA 3D
======================================================================

Usar PerspectiveCamera.

Recomendação de controle:
usar CameraControls disponível no ecossistema Drei/camera-controls.

Comportamento desejado:

LMB:
- selecionar;
- mover tokens/objetos quando em ferramenta adequada.

RMB:
- pan/truck, preservando a sensação da VTT atual.

MMB ou Alt + RMB:
- orbit/rotação.

Scroll:
- aproximar/afastar.

Teclas opcionais:
- F: focar seleção;
- Home: enquadrar mapa;
- 1: visão superior;
- 2: visão isométrica;
- 3: visão baixa/cinematográfica.

Câmera precisa:
- ter target;
- impedir near/far inadequados;
- limitar distância mínima;
- limitar distância máxima;
- evitar entrar abaixo do chão por padrão;
- permitir GM desativar limites em modo edição.

35. ASSET PIPELINE PARA GLB
======================================================================

O asset system atual suporta imagens e áudio.

assetRoutes aceita:
- image/*
- audio/*
- application/octet-stream

PORÉM assetService usa uma allowlist MIME que hoje não contém GLB.
Portanto application/octet-stream acaba não sendo aceito pelo save.

ALTERAR cuidadosamente.

Adicionar MIME:
- model/gltf-binary -> glb
- model/gltf+json -> gltf (opcional)

RECOMENDAÇÃO:
Na primeira versão aceitar apenas GLB.

Por quê:
GLB é um arquivo único.
.gltf pode depender de:
- .bin;
- texturas externas;
- múltiplos arquivos.

Isso complicaria armazenamento.

Suportar também application/octet-stream SOMENTE se:
- filename terminar em .glb;
- cabeçalho do arquivo for validado.

Validar magic do GLB:
primeiros bytes correspondem a "glTF".

Não aceitar arquivo arbitrário disfarçado.

      light => light.visibility === "public"
    ),
    events: scene.events.filter(
      event => event.isPubliclyKnown
    )
  };
}

Não copiar exatamente sem normalização.
É apenas o comportamento esperado.

======================================================================

======================================================================

======================================================================
142. NAVMESH
======================================================================

Só considerar navmesh se houver:
- movimentação livre complexa;
- modelos arquitetônicos importados;
- NPC automático.

Para VTT grid-based, grid + wall edges é suficiente e mais fácil de sincronizar.

======================================================================
143. OBJETO 3D IMPORTADO NÃO DEVE DEFINIR REGRA SOZINHO
======================================================================

Um GLB visual de parede não significa automaticamente blocksMovement.

Regra e visual precisam ser separados.

SceneObject:
- mesh visual;
- collider;
- blocksVision;
- blocksMovement.

Isso permite:
- modelo bonito;
- collider simples;
- server validar sem carregar Three.js.

======================================================================
144. SERVER NÃO DEVE RENDERIZAR THREE.JS
======================================================================

Backend não precisa de Three.js para regra comum.

Usar geometria simples shared:
- Box footprint;
- segment;
- circle;
- floor.

Evitar carregar GLB no Node para cada movimento.

Client cuida do visual.
Server cuida da regra.

======================================================================

Regra:
hinge + state + collider segment.

Excelente princípio para todo o projeto.
